## 一、架构设计原则（为什么这样设计）

### 1.1 面向初级开发者的可读性优先
- **每个模块有明确的边界**：模块之间通过接口通信，不直接操作对方内部状态
- **命名即注释**：函数名、变量名要一眼看出用途，避免缩写
- **TypeScript 类型即文档**：所有公共接口必须有 interface/type 定义

### 1.2 渐进式架构
- **v1 先跑通，v2 再优化**：v1 使用 Mock 数据，架构上预留真实 API 的替换点
- **不要过度设计**：能用简单方案解决的，不用复杂方案
- **一个文件一个职责**：不要写万能文件

### 1.3 状态管理单一来源
- **所有跨组件共享状态走 Zustand**：禁止用 props drilling 传递超过 2 层
- **本地状态用 useState**：只在组件内部使用的状态不放入 Store
- **持久化状态统一走 Persistence Layer**：不要散落在各处直接读写文件

## 二、技术栈一览（PRD 已确定）

| 层级 | 技术选型 | 版本要求 | 说明 |
|------|---------|---------|------|
| 桌面框架 | Electron | v42+ | 主进程(Node.js) + 渲染进程(Chromium) + Preload 脚本 |
| 前端框架 | React | v18+ | 函数式组件 + Hooks，不用 Class 组件 |
| 开发语言 | TypeScript | v5.0+ | 严格模式开启，不允许隐式 any |
| 构建工具 | Vite | v6+ | 开发服务器 + 生产打包 |
| 状态管理 | Zustand | v5+ | 轻量，无样板代码，TypeScript 友好 |
| 样式方案 | Tailwind CSS | v4+ | Utility-first CSS，不用写 CSS 文件 |
| 代码规范 | ESLint + Prettier | 最新 | 提交前自动格式化 |
| 图标库 | Lucide React | 最新 | 统一使用 Lucide 图标 |

## 三、核心架构决策（已确认）

| 决策点 | 选择方案 | 理由 |
|--------|---------|------|
| Mock 工具层位置 | **渲染进程直接调用** | v1 快速迭代，无 IPC 开销；v2 迁移到主进程时只需改服务层实现 |
| 行情看板 ↔ 聊天联动 | **Zustand 全局状态** | 与现有状态管理一致，可追踪、可持久化 |
| 持久化文件组织 | **每 Session 独立 JSON 文件** | 避免单文件膨胀，便于手动备份 |
| 技术文档结构 | **按模块拆分** | 维护更新方便，新人可按需阅读 |
| 个股链接渲染 | **前端正则解析** | v1 简单可靠，Agent 返回纯文本即可 |

## 五、关键约定（所有人必须遵守）

### 5.1 命名规范
- **文件命名**：PascalCase（组件）、camelCase（工具函数）、kebab-case（配置文件）
- **组件命名**：必须以功能命名，如 `MarketOverview`、`ChatMessageBubble`
- **Store 命名**：`useXxxStore`，State interface 命名 `XxxState`
- **IPC 通道命名**：`domain:action`，如 `session:create`、`file:read`

### 5.2 导入顺序
每个文件的导入按以下顺序排列，用空行分隔：
```typescript
// 1. React 内置
import { useState, useCallback } from 'react';

// 2. 第三方库
import { create } from 'zustand';

// 3. 项目内绝对路径（@/ 别名）
import { useSessionStore } from '@/stores/useSessionStore';

// 4. 项目内相对路径
import { MarketCard } from './MarketCard';
```

### 5.3 错误处理
- **同步代码**：用 try-catch，错误上报到全局错误处理
- **异步代码**：用 async-await + try-catch，不要用 .catch()
- **IPC 调用**：主进程必须返回 `{ success: boolean, data?, error? }` 格式
- **用户可见错误**：用 Toast 通知，不要用 console.error 代替

### 5.4 类型安全
- **禁止 any**：除了第三方库的类型缺失处，项目代码不允许用 `any`
- **必须导出类型**：所有公共函数的参数和返回值必须有类型标注
- **枚举用联合类型**：`type Theme = 'dark' | 'light'` 而不是 enum
