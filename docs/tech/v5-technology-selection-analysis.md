## 选型一：Shell 执行方案

### 方案 A：child_process.spawn（一次性执行）

**产品视角**
- **优点**：
  - 开发周期短（1-2 天），最快让客户看到"Agent 能执行命令"
  - 用户等待时间短，命令执行完立即返回结果，体验干脆
  - 足够覆盖 95% 投研场景：跑 Python 脚本、查看文件、git 操作
- **缺点**：
  - 不支持交互式程序（vim、python REPL、htop），用户如果习惯交互终端会失望
  - 复杂管道命令（`cat a.txt | grep x | wc -l`）需要额外处理

**技术视角**
- **优点**：
  - Node.js 内置，零依赖、零体积增加
  - 跨平台原生支持（Windows `spawn` 自动处理 `.cmd` / `.exe`）
  - 安全可控：一次性执行，执行完进程自动销毁，无残留
- **缺点**：
  - stdout/stderr 是流式数据，需要手动拼接和截断
  - 无法获取命令的实时输出（只能等执行完一次性返回）

### 方案 B：node-pty（伪终端）

**产品视角**
- **优点**：
  - 能跑交互式程序，体验最接近真实终端
  - 支持颜色输出、光标控制、curses 界面（如 htop）
- **缺点**：
  - 开发复杂度高（需要终端模拟器 UI）
  - 用户可能误操作进入交互状态导致 Agent "卡死"（如打开了 vim 不知道怎么退出）
  - 产品定位模糊：我们是 Agent 还是终端模拟器？

**技术视角**
- **优点**：
  - 真正的 TTY，支持所有终端功能
- **缺点**：
  - +2MB 体积；Windows 需特殊处理（conpty）
  - 安全风险更高：伪终端可以执行任意命令，包括逃逸沙箱的攻击
  - 需要额外维护终端状态（光标位置、屏幕缓冲区）

### 决策建议

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 开发周期 | 1-2 天 | 1-2 周 |
| 用户体验（投研场景） | 足够 | 过度 |
| 安全风险 | 低 | 高 |
| 体积影响 | 0 | +2MB |
| 未来扩展性 | 可平滑升级到 B | 一步到位 |

**联合推荐：方案 A**。v5 的核心目标是"让 Agent 能执行命令"，不是"做一个终端模拟器"。方案 A 足够验证产品价值，且为方案 B 预留了升级空间（未来需要交互式时再引入 node-pty）。

**关键妥协点**：管道命令可以通过包装 `sh -c "cat a.txt | grep x"` 来支持，不需要完整伪终端。

## 选型二：向量数据库

### 方案 A：Vectra（纯 TypeScript）

**产品视角**
- **优点**：
  - 用户完全无感知，后台静默运行，无需任何配置
  - 首次启动无延迟（数据从 JSON 加载，毫秒级）
  - 索引损坏概率低，且损坏后可后台自动重建
- **缺点**：
  - 极端大数据量（>5000 条记忆）时检索速度下降
  - 无 SQL 查询能力，复杂统计需要代码实现

**技术视角**
- **优点**：
  - 纯 TypeScript，零原生依赖，Electron 打包零坑
  - 内置 HNSW 索引，API 极简（`add` / `query` / `remove`）
  - 自动序列化为 JSON，无需额外持久化代码
- **缺点**：
  - 单线程，无法利用多核
  - HNSW 实现相对简单，召回率不如 faiss
  - 社区较小，长期维护存在不确定性

### 方案 B：SQLite + sqlite-vss

**产品视角**
- **优点**：
  - SQLite 是地球上最稳定的数据库，用户数据几乎不可能损坏
  - 可以用 SQL 做复杂统计（"我最近一个月关注了多少只股票"）
- **缺点**：
  - 原生模块编译失败时，整个语义记忆功能完全不可用
  - 如果用户环境缺少编译工具链，安装体验差

**技术视角**
- **优点**：
  - vss 扩展基于 faiss，向量检索性能强
  - SQL 生态丰富，可以 JOIN 其他业务表
- **缺点**：
  - **Electron 打包头号坑**：原生模块需要为每个平台预编译二进制
  - 体积 +5MB
  - 开发和 CI 需要处理多平台编译矩阵（win32-x64、darwin-arm64、linux-x64 等）

### 方案 C：纯内存 + 本地 JSON（暴力扫描）

**产品视角**
- **优点**：
  - 极快（内存操作）
- **缺点**：
  - 应用重启时加载慢（需要重新 embedding 所有记忆）
  - 数据量大时检索明显卡顿

**技术视角**
- **优点**：
  - 最简单，100 行代码搞定
- **缺点**：
  - 无索引，O(N) 暴力扫描，1000 条以上检索 >1 秒
  - 内存占用随数据量线性增长

### 决策建议

| 维度 | Vectra | SQLite-vss | 纯内存 |
|------|--------|-----------|--------|
| Electron 兼容性 | 完美 | 坑多 | 完美 |
| 打包复杂度 | 零 | 高 | 零 |
| 单用户性能（500 条） | <100ms | <50ms | <500ms |
| 单用户性能（5000 条） | <300ms | <100ms | >3s |
| 体积 | +50KB | +5MB | 0 |
| 数据可靠性 | 中（JSON） | 极高 | 低 |

**联合推荐：方案 A（Vectra）**。

理由：
1. **单用户记忆量预期**：一个重度用户 1 年产生的记忆片段约 500-1000 条，Vectra 的 HNSW 在此量级下性能完全够用（<300ms）
2. **Electron 原生模块是噩梦**：SQLite-vss 虽然性能更好，但开发和打包的隐性成本可能消耗整整一周。v5 的核心目标是"快速验证语义记忆的产品价值"，不是"搭建完美向量数据库"
3. **迁移成本低**：如果未来数据量突破 5000 条，Vectra → SQLite-vss 的迁移只需重写 `vectorStore.ts` 一个文件，上层业务代码零改动

**兜底方案**：在 `vectorStore.ts` 中抽象接口，预留 SQLite-vss 的替换点。

## 选型三：Embedding 模型

### 方案 A：transformers.js + all-MiniLM-L6-v2（本地）

**产品视角**
- **优点**：
  - 完全离线，不需要 API Key，保护隐私（投研对话常涉及持仓信息）
  - 无网络依赖，地铁/飞机上也能正常使用
  - 零持续成本（无 API 调用费）
- **缺点**：
  - 首次使用需下载模型（~20MB），有"Loading..."等待
  - 低配置电脑（老旧的 4 核 CPU）推理可能慢（500ms+/条）

**技术视角**
- **优点**：
  - ONNX Runtime Web 在 CPU 上运行稳定
  - 384 维向量，存储效率高
  - 支持中文（虽然不是专门的中文模型，但跨语言效果可接受）
- **缺点**：
  - 打包体积 +20MB（或改为按需下载）
  - 推理速度不如云端 GPU（100-300ms vs 20-50ms）

### 方案 B：调用 Kimi/OpenAI Embedding API（云端）

**产品视角**
- **优点**：
  - 速度快（云端 GPU，20-50ms）
  - 模型效果好（text-embedding-3-large 等专门优化的模型）
  - 无本地体积
- **缺点**：
  - 需要联网，无网环境完全不可用
  - **隐私风险**：用户对话内容需要上传到第三方服务器
  - 有 API 成本（按 token 计费，重度用户每月可能产生 $1-5 费用）

**技术视角**
- **优点**：
  - 实现简单（一个 HTTP POST）
  - 模型效果通常比本地轻量模型好 10-20%
- **缺点**：
  - 网络失败时整个记忆系统瘫痪（需要降级策略）
  - 增加了 LLM API 的并发压力

### 方案 C：Ollama 本地 Embedding（外部服务）

**产品视角**
- **优点**：
  - 模型选择多（nomic-embed、m3e 等中文优化模型）
  - 效果通常比 MiniLM 好
- **缺点**：
  - 用户需要额外安装 Ollama，使用门槛高
  - 非技术用户根本不知道怎么装

**技术视角**
- **优点**：
  - 本地 HTTP API，易于集成
- **缺点**：
  - 外部进程管理复杂（启动、监控、重启）
  - 需要处理端口冲突

### 决策建议

| 维度 | transformers.js | Kimi API | Ollama |
|------|-----------------|----------|--------|
| 隐私 | 完美 | 有风险 | 完美 |
| 离线可用 | 是 | 否 | 是 |
| 首次体验 | 需下载模型 | 即开即用 | 需安装 Ollama |
| 持续成本 | 0 | $1-5/月 | 0 |
| 推理速度 | 100-300ms | 20-50ms | 50-200ms |
| 中文效果 | 可接受 | 好 | 好 |
| 用户门槛 | 低 | 极低 | 高 |

**联合推荐：方案 A（transformers.js），但模型改为按需下载。**

理由：
1. **隐私是投研产品的红线**：用户对话中可能包含真实持仓、交易策略，上传到第三方是不可接受的风险
2. **按需下载解决体积问题**：模型不打包进安装包，首次使用记忆功能时后台下载（20MB，5-10 秒），安装包体积零增加
3. **效果够用**：all-MiniLM-L6-v2 在中文文本相似度任务上效果可接受（与专门中文模型差距 <15%），对于"找相关记忆"这个场景完全够用

**兜底机制**：在设置中提供"使用云端 Embedding API"开关。如果用户本地模型下载失败或性能太差，可手动切换到 Kimi API。

## 选型四：Embedding 模型分发方式（方案 A 的细分）

### 4a. 打包进安装包（推荐）
- **产品**：首次使用零等待，离线环境立即可用；无需下载进度 UI
- **技术**：安装包 +20MB；模型文件随应用一起分发，路径稳定
- **适用性**：语义记忆是 v5 核心功能，用户安装就是冲着记忆来的，不存在"不用记忆"的用户

### 4b. 按需下载（首次使用时后台下载）
- **产品**：安装包体积小；首次使用记忆功能时有 5-10 秒下载等待
- **技术**：需要实现下载进度 UI、断点续传、失败重试、降级逻辑
- **风险**：用户首次在离线环境使用记忆功能时直接不可用

**联合推荐：4a（打包进安装包）**。

理由：语义记忆是 v5 核心卖点，20MB 在现代网络环境下感知极弱（100Mbps 下约 2 秒）。按需下载的复杂性和首次离线不可用的风险，远大于 20MB 体积增益。

## 选型五：Shell 危险命令确认方式

### 5a. 阻塞式弹窗（同步 dialog）
- **产品**：用户必须点击确认才能继续，最安全，最不容易误操作
- **技术**：Electron `dialog.showMessageBoxSync`，一行代码实现
- **体验**：UI 会冻结等待用户操作，但 Shell 执行不是高频操作，可接受

### 5b. 非阻塞通知 + 延迟执行（5 秒倒计时取消）
- **产品**：体验更流畅，用户不需要立即响应
- **技术**：复杂，需要定时器 + 全局状态管理 + 取消逻辑
- **风险**：用户可能没注意到通知，导致危险命令被执行

**联合推荐：5a（阻塞式弹窗）**。安全类产品，宁可牺牲一点体验也要保证零误操作。

## 选型六：浏览器自动化（客户提过，v5 不做但需说明理由）

### 为什么 v5 不做？

| 风险 | 说明 |
|------|------|
| **体积膨胀** | Puppeteer + Chromium 额外 +150MB，安装包从 80MB → 230MB+ |
| **法律风险** | 自动抓取东方财富、同花顺等金融网站数据，大概率违反 ToS |
| **维护噩梦** | 网页 DOM 结构一变，选择器就失效，需要持续维护 |
| **产品定位** | v5 目标是"Agent 能执行命令 + 有记忆"，浏览器自动化是锦上添花 |

### v6 预埋方案（如果未来要做）

| 方案 | 体积 | 复杂度 | 推荐度 |
|------|------|--------|--------|
| Puppeteer | +150MB | 中 | 不推荐（体积太大） |
| Playwright | +150MB | 中 | 不推荐 |
| **CDP（Chrome DevTools Protocol）** | 0（复用 Electron 自带 Chromium） | 高 | **推荐** |
| 截图 + 视觉 LLM | 0 | 高 | 备选（需多模态模型） |

**CDP 方案**：Electron 的 `webContents` 原生支持 CDP，可以控制隐藏窗口执行 `Page.navigate`、`DOM.querySelector`、`Runtime.evaluate`，零额外体积。

## 最终选型汇总（已确认）

| 模块 | 最终方案 | 备选/降级 |
|------|---------|----------|
| Shell 执行 | `child_process.spawn`（内置） | 未来可升级 node-pty |
| 向量数据库 | `vectra`（纯 TS，JSON 序列化持久化） | 未来数据量大时迁移 SQLite-vss |
| Embedding | `transformers.js` + `all-MiniLM-L6-v2`（**打包进安装包**） | 设置中提供 Kimi API 降级开关 |
| 危险命令确认 | 阻塞式弹窗（`dialog.showMessageBoxSync`） | — |
| 浏览器自动化 | **v5 不做**，v6 预埋 CDP | — |
| 记忆归档触发 | 新建 Session（主力）+ 关闭应用（兜底）+ 手动按钮（辅助） | — |
| 结构化数据存储 | 保持现有 JSON/localStorage（Vectra 只管向量） | 未来需要复杂查询时迁移 SQLite/PGLite |
