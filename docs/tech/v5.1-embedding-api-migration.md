# v5.1 Embedding 架构迁移方案：本地模型 → 智谱 Embedding API

> 状态：待评审  
> 版本：v5.1  
> 日期：2026-06-10  
> 决策背景：本地 transformers.js + ONNX Runtime WASM 方案在 Electron 渲染进程中持续遭遇 `protobuf parsing failed` 等底层兼容性问题，排查成本极高且无法保证跨平台稳定性。项目已接入智谱（BigModel）LLM API，复用其 Embedding-3 API 是更务实的架构选择。

---

## 一、目标

1. **彻底移除** `@xenova/transformers` 依赖及本地模型文件（~40MB+）
2. **接入** 智谱 Embedding-3 API，实现云端文本向量化
3. **保持** 现有 Vectra 向量存储、记忆归档、语义检索等上层业务逻辑不变
4. **优化** 批量 Embedding 调用效率（利用智谱单次 64 条批量接口）

---

## 二、技术方案概述

| 项目 | 变更前（v5） | 变更后（v5.1） |
|------|-------------|---------------|
| Embedding 模型 | `Xenova/all-MiniLM-L6-v2`（本地 WASM） | `embedding-3`（智谱云端 API） |
| 向量维度 | 固定 384 维 | **可配置 256/512/1024/2048，默认 512 维** |
| 推理位置 | Electron Renderer 进程（CPU WASM） | 智谱云端 GPU |
| 首响延迟 | 2-5s（WASM 编译+模型加载） | ~100-300ms（HTTP RTT） |
| 依赖体积 | +~40MB（模型+WASM） | +0MB |
| 离线可用 | 是 | 否（但 LLM 已要求联网） |
| 多语言 | 英文为主 | **中英双语优化** |
| API 成本 | 0 | **0.5 元 / 百万 Tokens**（月均 < 1 元） |

### API 端点

```
POST https://open.bigmodel.cn/api/paas/v4/embeddings
Authorization: Bearer {apiKey}
Content-Type: application/json

{
  "model": "embedding-3",
  "input": "需要向量化的文本",
  "dimensions": 512
}
```

响应中的 `data[0].embedding` 即为向量数组。

- `generateEmbeddings(texts)`：**批量调用**，将多条文本打包为一次 API 请求（智谱支持单次最多 64 条），大幅优化归档性能

- 导出 `getVectorDimension()`：改为返回常量 `DEFAULT_DIMENSION`
- 导出 `isModelLoading()` / `isModelReady()` / `preloadModel()`：改为无操作 stub（返回 `false`/`true`/空 Promise），保持上层调用兼容

**关键代码结构**：

```typescript
const DEFAULT_DIMENSION = 512
const DEFAULT_EMBEDDING_MODEL = 'embedding-3'
const MAX_BATCH_SIZE = 64

interface EmbeddingConfig {
  apiKey: string
  baseUrl: string
  model: string
  dimensions: number
}

// 从 usePreferenceStore 获取配置（或通过参数传入）
const getEmbeddingConfig = (): EmbeddingConfig => {
  const { llmConfig } = usePreferenceStore.getState()
  return {
    apiKey: llmConfig.apiKey,
    baseUrl: llmConfig.baseUrl,
    model: llmConfig.embeddingModel || DEFAULT_EMBEDDING_MODEL,
    dimensions: llmConfig.embeddingDimensions || DEFAULT_DIMENSION,
  }
}

// 内部：调用智谱 API
const callEmbeddingAPI = async (
  texts: string[],
  config: EmbeddingConfig
): Promise<number[][]> => {
  // 过滤空文本
  const validTexts = texts.filter(t => t.trim().length > 0)
  if (validTexts.length === 0) return texts.map(() => fallbackEmbedding(''))

  const response = await fetch(`${config.baseUrl}/embeddings`, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${config.apiKey}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      model: config.model,
      input: validTexts,
      dimensions: config.dimensions,
    }),
  })

  if (!response.ok) {
    const err = await response.text()
    throw new Error(`Embedding API error ${response.status}: ${err}`)
  }

  const data = await response.json()
  // 按 index 排序，确保顺序与输入一致
  const embeddings = data.data
    .sort((a: any, b: any) => a.index - b.index)
    .map((item: any) => item.embedding as number[])

  return embeddings
}
```

**⚠️ 注意**：`usePreferenceStore.getState()` 是同步读取，但 embeddingService.ts 目前不依赖 React hook 规则，可直接调用。

## 四、数据迁移策略

### 核心问题：向量维度从 384 → 512，旧索引失效

Vectra 使用余弦相似度进行检索，要求所有向量的维度一致。384 维的旧向量与 512 维的新向量**无法共存**。

### 迁移方案（推荐：自动重建）

1. **应用启动时检测维度变化**
   - 在 `vectorStore.ts` 的 `getIndex()` 中，读取索引元数据（如果 Vectra 支持存储自定义 metadata）
   - 或者，在 `userData` 目录下创建一个独立的 `vector-config.json`，记录当前维度

2. **如果检测到维度变化**：
   - 备份旧索引目录（重命名为 `vector-memory-backup-{timestamp}`）
   - 删除旧索引目录 `vector-memory/`
   - 创建新索引（Vectra 的 `createIndex` 不限制维度，维度由插入的向量决定）
   - 写入新配置 `vector-config.json`：`{ dimension: 512, createdAt: '...' }`

3. **显式偏好数据不受影响**
   - `memory.json` 中的显式偏好（风险偏好、关注板块等）**不依赖向量维度**，完全保留
   - 只有 Vectra 中的语义记忆需要重建

4. **重建后用户感知**
   - 首次启动 v5.1 时，旧的历史语义记忆会丢失（需要重新通过对话归档积累）
   - 但用户的核心偏好（memory.json）仍然保留
   - 可在更新日志中说明此行为

### 替代方案（不推荐）：保留双索引

- 同时维护 384 维和 512 维两个索引
- 查询时分别查，合并结果
- 复杂度极高，收益极低，**不建议**

## 五、批量调用优化（性能关键）

### 当前问题

`memoryArchive.ts` 中的归档逻辑：
```typescript
for (const fragment of fragments) {
  const vector = await generateEmbedding(fragment.content) // 单条调用
}
```

如果一次 Session 提取了 10 个片段，将产生 **10 次 HTTP 请求**。

### 优化方案

修改 `memoryArchive.ts` 的归档逻辑：

```typescript
// 批量生成所有片段的向量
const contents = fragments.map(f => f.content)
const vectors = await generateEmbeddings(contents) // 一次 API 调用

for (let i = 0; i < fragments.length; i++) {
  const vector = vectors[i]
  // 去重检查...
}
```

`generateEmbeddings` 内部实现：
- 如果 `texts.length <= MAX_BATCH_SIZE`（64），直接一次 API 调用
- 如果超过 64，分块处理（chunk），每块 64 条，并发调用（控制并发数 ≤ 3，避免限流）

## 六、潜在风险与应对措施

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| **旧向量索引与新维度不兼容** | 高 | 高 | 启动时自动检测维度变化，备份并重建索引 |
| **Embedding API 网络失败** | 中 | 高 | 保留 fallback 伪向量逻辑，API 失败时自动降级，记录 warn 日志 |
| **智谱 API 限流（50 并发）** | 低 | 中 | 批量调用（单次最多 64 条），归档时控制并发数 ≤ 3 |
| **CORS 预检失败** | 低 | 中 | `open.bigmodel.cn` 已在 CSP connect-src 中允许，无需额外配置 |
| **向量维度选择不当** | 低 | 低 | 默认 512 维，设置页提供 256/512/1024/2048 选项及场景建议 |
| **API Key 未配置时 Embedding 失败** | 中 | 中 | 如果 `apiKey` 为空，直接返回 fallback 向量，不发起 HTTP 请求 |
| **打包后模型文件残留** | 低 | 低 | 清理 `electron-builder.yml` 和 `package.json`，确保不打包残留文件 |
| **调试面板依赖旧模型状态** | 中 | 低 | 同步修改 `MemoryDebugPanel.tsx`，移除模型加载状态 UI |
| **设置页缺少 Embedding 配置** | 中 | 中 | 在 `LLMSettings.tsx` 中新增维度选择器 |
| **成本超支（极端场景）** | 极低 | 低 | 月均 < 1 元，可忽略；如需监控，可在日志中记录每次调用的 token 消耗 |

## 九、实施建议

1. **先清理，后重建**：先删除无用文件和依赖，再写新的 embeddingService，避免混淆
2. **批量优化优先**：`generateEmbeddings` 的批量实现是性能关键，务必在首次提交中包含
3. **索引重建提示**：在设置页维度切换时，给用户明确的确认弹窗，避免误操作丢失历史记忆
4. **保留 fallback**：即使云端方案稳定，fallback 伪向量仍是应对网络异常的最后防线
5. **日志完整**：API 调用失败时，记录 HTTP status、错误响应体前 200 字符，便于后续排查
