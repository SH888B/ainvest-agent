## 一、问题根因分析

### BUG-01：自动归档不稳定

**根因**：自动归档逻辑嵌入在 `SessionSidebar.handleCreateSession` 中，与 Session 创建共享同一个用户操作路径。归档是异步重操作（LLM 提取 + Embedding API + 写入 Vectra），创建是同步轻操作，两者耦合导致：

1. **竞态**：异步归档的 `.then(updateArchivedCount)` 与用户后续操作可能交错
2. **静默失败**：`catch` 只打 console.error，用户无感知
3. **阻塞风险**：如果归档意外阻塞，可能影响 `isCreating` 状态流转

**修复策略**：引入配置开关，默认关闭自动归档。代码保留不删除，通过运行时条件跳过。

## 二、技术方案

### 2.1 新增配置项：`autoArchiveOnNewSession`

**存储位置**：`usePreferenceStore`（已有 persist）

```typescript
// src/renderer/stores/usePreferenceStore.ts

interface PreferenceState {
  llmConfig: LLMConfig
  isConfigValid: boolean
  // ... 已有字段
  /** v6.0.1: 新建 Session 时自动归档上一个（默认关闭） */
  autoArchiveOnNewSession: boolean
  setAutoArchiveOnNewSession: (val: boolean) => void
}
```

**默认值**：`false`（关闭）

**持久化**：随 `usePreferenceStore` 的 persist 自动保存到 localStorage

### 2.2 SessionSidebar 条件判断

```typescript
// src/renderer/features/session/SessionSidebar.tsx

const handleCreateSession = async () => {
  const previousSessionId = currentSessionId
  const newId = createSession()
  if (!newId) return

  // v6.0.1: 仅在开关开启时自动归档
  if (autoArchiveOnNewSession && previousSessionId && isConfigValid) {
    const messages = getMessages(previousSessionId)
    const session = sessions.find((s) => s.id === previousSessionId)
    const archivedCount = session?.archivedMessageCount || 0

    if (messages.length > archivedCount) {
      archiveSession({ ... })
        .then(() => { updateArchivedCount(...) })
        .catch((err) => { console.error('[SessionSidebar] 自动归档失败:', err) })
    }
  }
}
```

**关键变化**：只在 `autoArchiveOnNewSession === true` 时执行归档代码块，其余逻辑完全不变。

## 五、追加问题技术方案

### BUG-03：设置弹窗关闭后输入框无法输入

**根因**：模态对话框（SettingsPage）关闭后，焦点未正确归还给聊天输入框。可能原因：
1. React 模态组件的焦点还原机制在 Electron 中行为不一致
2. `SettingsPage` 使用 `onClose` 回调关闭，但没有手动 `focus()` 输入框
3. Electron 的 `BrowserWindow` 焦点管理与 React 的焦点管理存在冲突

**修复方案**：在 `SettingsPage` 关闭时，主动将焦点还给输入框：

```typescript
// ChatPanel.tsx
const inputRef = useRef<HTMLTextAreaElement>(null)

const handleCloseSettings = () => {
  setSettingsOpen(false)
  // 关闭设置页后，延迟一帧将焦点还给输入框
  requestAnimationFrame(() => {
    inputRef.current?.focus()
  })
}
```

**改动文件**：`ChatPanel.tsx`（添加 inputRef + 修改 onClose 回调）

---

### BUG-04：web.browse 工具参数提取失败

**根因分析**：`BROWSER_EXTRACTION_PROMPT` 要求 LLM 从自然语言构造完整 URL（如 `"https://xueqiu.com/S/SH300750"`），但 LLM 不一定知道目标网站的 URL 格式。这与其他工具的参数提取有本质区别：

| 工具 | LLM 任务 | 可靠性 |
|------|---------|--------|
| `market.query` | 提取股票代码（6位数字） | 高 |
| `shell.execute` | 提取命令名 | 高 |
| `web.browse` | **构造完整 URL** | **低** |

主流方案（OpenAI WebSearchTool、Tavily）采用"搜索优先"模式：LLM 生成搜索关键词，搜索引擎返回多源聚合结果。我们需要重构。

## 六、web.browse "搜索优先"重构方案对比

> 架构师 + Prompt 工程师联合分析

### 方案 A：轻量搜索兜底（最小改动）

**思路**：保留当前 LLM 提取 URL 的路径，增加本地搜索 URL 构造作为兜底。

```
用户输入 → 意图识别 → extractToolArgs() 
                         ├─ 返回有效 url → 直接用（现有逻辑）
                         └─ url 为空 → 本地从输入提取关键词 → 构造搜索 URL
```

**改动点**：

| 文件 | 改动 |
|------|------|
| `agentEngine.ts` | `extractToolArgs` 返回空后，调用 `buildSearchUrl(query)` 兜底 |
| `browser.ts` | 新增 `buildSearchUrl(query, domainHint)` 函数 |
| `BROWSER_EXTRACTION_PROMPT` | 调整：优先返回 url，其次返回 query |

**Prompt 变更**：

```
旧：从用户输入中提取要访问的网页 URL 和提取方式。只返回 JSON 格式：{"url": "网页URL", "action": "snapshot 或 screenshot"}

新：从用户输入中提取搜索关键词或目标 URL。返回 JSON 格式：
- 如果能确定具体 URL：{"url": "完整URL", "action": "snapshot"}
- 如果无法确定 URL：{"query": "搜索关键词", "domain": "xueqiu.com"}
- action 默认 snapshot
```

**搜索 URL 模板**：

```typescript
const SEARCH_URL_TEMPLATES = {
  'xueqiu.com':    'https://xueqiu.com/k?q={query}',
  'eastmoney.com': 'https://so.eastmoney.com/news/s?keyword={query}',
  'cls.cn':        'https://www.cls.cn/search?keyword={query}',
  'sina.com.cn':   'https://search.sina.com.cn/?q={query}',
  // ... 其他白名单域名
}
```

| 优点 | 缺点 |
|------|------|
| 改动最小（~30 行） | Prompt 同时要求 url 和 query，LLM 可能混淆 |
| 兼容旧逻辑 | 仍依赖 LLM 提取关键词，只是把"构造 URL"转为"提取关键词" |
| 可快速验证 | 没有改变工具定义的本质（仍然是 `browser.open`） |

---

### 方案 B：搜索关键词优先（推荐）

**思路**：将工具参数从 `url` 改为 `query` + `domain`，LLM 只需生成搜索关键词，本地构造搜索 URL。如果 LLM 直接返回了 URL 也可以用。

```
用户输入 → 意图识别 → extractToolArgs()
                         ├─ 返回 query → 本地构造搜索 URL → browser.open(searchUrl)
                         ├─ 返回 url → 直接 browser.open(url)（兼容）
                         └─ 都为空 → 本地从输入提取关键词兜底 → 构造搜索 URL
```

**改动点**：

| 文件 | 改动 |
|------|------|
| `prompts.ts` | `BROWSER_EXTRACTION_PROMPT` 改为要求返回 `query` + `domain` |
| `agentEngine.ts` | 新增 `buildSearchUrl` 逻辑，处理 `query` / `url` 两种参数 |
| `browser.ts` | `executeBrowserTool` 接受 `query` 参数，内部构造 URL |

**Prompt 变更**：

```
从用户输入中提取搜索关键词。返回 JSON 格式：{"query": "搜索关键词", "domain": "目标域名", "action": "snapshot"}

规则：
- query：从用户输入中提取核心搜索词（如"宁德时代 研报 最新"）
- domain：根据内容类型推荐域名
  - 研报/个股分析 → eastmoney.com
  - 新闻/快讯 → cls.cn
  - 综合/不确定 → xueqiu.com
- action 默认 snapshot

示例：
- "查一下雪球的宁德时代研报" → {"query": "宁德时代 研报", "domain": "xueqiu.com"}
- "最新财经新闻" → {"query": "财经 新闻 最新", "domain": "cls.cn"}
- "帮我看看东方财富的茅台页面" → {"query": "贵州茅台", "domain": "eastmoney.com"}
```

| 优点 | 缺点 |
|------|------|
| LLM 生成关键词比构造 URL 可靠得多 | 改动比方案 A 大（~50 行） |
| Prompt 职责单一清晰 | 搜索结果页内容可能比较杂乱（不是精确页面） |
| 兼容直接返回 URL 的情况 | 搜索 URL 模板需要验证各网站是否可用 |
| 对齐主流方案（搜索优先） | |

---

### 方案 C：独立搜索工具（长期方案，v6.1+）

**思路**：将 `web.browse` 拆分为两个工具：`web.search`（搜索）和 `web.fetch`（直接访问），对齐 Browserbase 的 Search/Fetch 双 API 设计。

```
意图识别 → web.search → 搜索 API → 返回多源摘要
                      或
意图识别 → web.fetch → CDP 访问具体 URL → 返回页面内容
```

**改动点**：

| 文件 | 改动 |
|------|------|
| `intentClassifier.ts` | 新增 `web.search` 意图 |
| `tools/search.ts` | 新建搜索工具 |
| `tools/browser.ts` | 重命名为 `web.fetch` |
| `prompts.ts` | 新增搜索工具的参数提取 Prompt |
| `agentEngine.ts` | 适配双工具 |

| 优点 | 缺点 |
|------|------|
| 职责分离，搜索和浏览独立演进 | 改动量大（~100+ 行） |
| 对齐行业最佳实践（Browserbase Search/Fetch） | 需要外部搜索 API（Tavily/SerpAPI）或自建 |
| 搜索可返回多源聚合结果 | v6.0.1 不适合做这么大的改动 |

### 方案对比总结

| 维度 | 方案 A（轻量兜底） | 方案 B（搜索优先）⭐ | 方案 C（独立搜索工具） |
|------|-------------------|---------------------|---------------------|
| 改动量 | ~30 行 | ~50 行 | ~100+ 行 |
| 可靠性 | 中 | 高 | 最高 |
| Prompt 复杂度 | 中（同时要求 url 和 query） | 低（只要求 query） | 低（各自独立） |
| 兼容旧逻辑 | 完全兼容 | 兼容（url 仍可用） | 不兼容（工具拆分） |
| 适合版本 | v6.0.1 轻量验证 | v6.0.1 正式方案 | v6.1+ |
| 对齐主流 | 部分 | 基本对齐 | 完全对齐 |

**建议**：v6.0.1 采用**方案 B**做轻量验证。如果搜索 URL 模板验证可行，v6.1 升级为方案 C。

## 八、追加问题技术方案（第二轮集成测试）

### BUG-07：CDP SPA 页面内容提取返回空

**根因**：`browserCDP.ts` 第 169 行在 `did-finish-load` 后固定等待 500ms 再提取内容。对于 SPA 页面（如雪球搜索页），`did-finish-load` 在初始 HTML 加载完成时触发，但 JS 渲染实际内容需要更长时间。500ms 远不够 SPA 完成渲染，导致 `document.body.innerText.length === 0`。

**修复方案**：将固定延迟改为智能轮询机制：

```typescript
// 旧：固定等待 500ms
await new Promise((resolve) => setTimeout(resolve, 500))

// 新：轮询等待内容出现，最长 5000ms
const MAX_CONTENT_WAIT_MS = 5000
const POLL_INTERVAL_MS = 500
const pollStart = Date.now()
let contentReady = false

while (!contentReady && (Date.now() - pollStart) < MAX_CONTENT_WAIT_MS) {
  await new Promise((resolve) => setTimeout(resolve, POLL_INTERVAL_MS))
  try {
    const { result: pollResult } = await this.debugger.sendCommand('Runtime.evaluate', {
      expression: 'document.body.innerText.length',
      returnByValue: true,
    })
    const textLength = pollResult?.value || 0
    if (textLength > 0) {
      contentReady = true
    }
  } catch {
    // 轮询失败继续等待
  }
}
```

**改动文件**：`src/main/services/browserCDP.ts`

**风险评估**：
- 非 SPA 页面：首次轮询即发现 textLength > 0，只需 ~500ms，与原逻辑基本一致
- SPA 页面：最长等待 5000ms，足够 JS 完成渲染
- 极端情况：如果页面 body 初始就有少量文本（如 loading 提示），可能提前结束。但 EXTRACTION_SCRIPT 会移除噪声元素，提取结果仍以实际内容为主

### BUG-08：意图分类器规则优先级错误

**根因**：`classifyIntentLocal` 使用 `for...of` 遍历 `LOCAL_RULES` 数组，返回**首个匹配**的规则。当同一输入匹配多个规则时，结果取决于规则在数组中的顺序，而非规则的置信度。

具体案例：`"搜索东方财富的贵州茅台新闻"` 同时匹配：
- `news.search` 规则（第 60-63 行）：`/(搜|搜索|查|查找).{0,5}(新闻|资讯|消息)/` → confidence 0.8
- `web.browse` 规则（第 146-149 行）：`/(查|搜索|看看|打开|浏览).{0,10}(网页|网站|研报|新闻|公告|雪球|东方财富|同花顺|财联社)/` → confidence 0.85

由于 `news.search` 在数组中排在 `web.browse` 之前，0.8 的匹配被返回，0.85 的匹配被跳过。

**修复方案**：将 `classifyIntentLocal` 改为遍历所有规则，返回最高置信度的匹配：

```typescript
// 旧：返回首个匹配
export const classifyIntentLocal = (text: string): IntentResult | null => {
  for (const rule of LOCAL_RULES) {
    if (rule.pattern.test(text)) {
      return { intent: rule.intent, confidence: rule.confidence }
    }
  }
  return null
}

// 新：返回最高置信度匹配
export const classifyIntentLocal = (text: string): IntentResult | null => {
  let bestMatch: IntentResult | null = null
  for (const rule of LOCAL_RULES) {
    if (rule.pattern.test(text)) {
      if (!bestMatch || rule.confidence > bestMatch.confidence) {
        bestMatch = { intent: rule.intent, confidence: rule.confidence }
      }
    }
  }
  return bestMatch
}
```

**改动文件**：`src/renderer/services/agent/intentClassifier.ts`

**影响分析**：
- **正面**：所有意图的匹配都基于置信度最优，不再依赖源码中的数组顺序
- **潜在影响**：某些之前被"先到先得"匹配的输入可能改变分类结果。但这些都是之前就不正确的结果（低置信度覆盖了高置信度），修复后行为更合理
- **性能**：从 O(1) 首匹配变为 O(n) 全遍历，但 LOCAL_RULES 仅 20+ 条，且都是正则匹配，耗时可忽略

### BUG-07 补充：SPA 搜索页内容提取不可靠 → 改用百度搜索

**问题**：BUG-07 的智能轮询修复后，雪球（xueqiu.com）和东方财富（eastmoney.com）的搜索页仍然提取到空内容。根因是这些 SPA 页面的内容渲染方式与普通 SSR 页面不同：

| 网站 | 渲染方式 | `innerText` 可提取性 | 实际测试 |
|------|---------|---------------------|---------|
| baidu.com | SSR（服务端渲染） | ✅ 立即可提取 | textLength > 0 |
| xueqiu.com | SPA + 懒加载 | ❌ 轮询 5s 仍为 0 | textLength: 0 |
| eastmoney.com | SPA + iframe | ❌ 内容在 iframe 中 | textLength: 0 |

**决策**：将默认搜索引擎从 `xueqiu.com` 改为 `baidu.com`。

百度搜索的优势：
1. **SSR 渲染**：`did-finish-load` 后 `document.body.innerText` 立刻有内容
2. **结果最全面**：百度搜索聚合了各网站的结果，包含新闻、研报、讨论等多种来源

### BUG-09：CDP Runtime.evaluate 编码问题导致内容提取始终为空（P0）

**现象**：百度搜索页轮询检测成功（`textLength: 2817`），但提取结果始终为空（`textLength: 0`）。同时标题乱码：`瀹佸痉鏃朵唬鐮旀姤_鐧哄害鎼滅储` = "宁德时代研报_百度搜索"。

**根因**：CDP `Runtime.evaluate` 存在编码问题，涉及中文的脚本表达式执行异常：

| 步骤 | 执行方式 | 结果 |
|------|---------|------|
| 轮询 `contentReady` | CDP + `innerText.length`（纯 ASCII 数字） | ✅ 无编码问题 |
| 标题 `getTitle()` | Electron 原生 API | ❌ 乱码 |
| 内容提取 `EXTRACTION_SCRIPT` | CDP + IIFE + 中文正则 | ❌ 静默报错，返回空串 |

CDP `Runtime.evaluate` 脚本报错时返回 `{ exceptionDetails: {...} }` 而非 `{ result: { value: ... } }`，原代码用 `result?.value || ''` 静默吞掉了错误。

同时，`EXTRACTION_SCRIPT` 中的 `el.remove()` 破坏性删除 DOM 元素，百度搜索结果容器可能被误删（匹配 `.ad` 选择器），也导致内容丢失。

**修复方案**：从 CDP 重构为 Electron 原生 `webContents.executeJavaScript()`：

1. **移除 CDP debugger**：不再 `attach('1.3')` / `detach()`，整个 `debugger` 字段删除
2. **executeJavaScript 替代 Runtime.evaluate**：
   - 无编码问题（Electron 原生 API，正确处理 UTF-8）
   - 有错误处理（脚本抛错会 reject Promise）
   - 不需要 CDP debugger
3. **简化提取脚本**：`EXTRACTION_SCRIPT` 改为 `document.body.innerText.slice(0, 8000)`（最小化浏览器侧逻辑）
4. **噪声过滤移到 Node.js 侧**：`cleanExtractedText()` 函数，中文正则在 Node.js 中无编码问题
5. **不做 DOM 删除**：不再使用 `el.remove()`，避免误删搜索结果容器

**改动文件**：`src/main/services/browserCDP.ts`

**架构变化**：

```
旧：CDP Runtime.evaluate（有编码问题 + 静默错误 + DOM 删除风险）
  attach('1.3') → Runtime.evaluate(复杂IIFE) → result?.value || ''

新：Electron executeJavaScript（无编码问题 + 正确错误处理 + 无 DOM 修改）
  executeJavaScript('document.body.innerText.slice(0,8000)') → cleanExtractedText()
```

### BUG-10：新 Session 首次提问后未自动更新名称

**根因**：`handleSend` 用 `useCallback` 闭包捕获 `sessions`。`createSession()` 调用 `set()` 更新 store 后，闭包中的 `sessions` 仍是旧值（不含新 session）。`sessions.find()` 返回 `undefined` → `autoRenameSession` 不触发。

**修复**：`createSession()` 后从 `useSessionStore.getState()` 获取最新 sessions：

```typescript
// 旧：用闭包中的旧 sessions
const session = sessions.find((s) => s.id === sessionId)

// 新：从 store 获取最新 sessions
const latestSessions = useSessionStore.getState().sessions
const session = latestSessions.find((s) => s.id === sessionId)
```
